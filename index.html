Algorithms

Mark-ready answerDefinition points
  • An algorithm is a solution to a problem.
  • It is expressed as a sequence of defined steps.
  • The steps should be clear and unambiguous, in the order in which they are carried out.
  • The algorithm must terminate after a finite number of steps and produce the required result.
Safe two-mark definition: “A solution to a problem, expressed as a sequence of clearly defined steps.”

Programming Basics

Mark-ready methodPreserve the design’s logic exactly
Translation Map each design feature
  • Convert each input / output step to INPUT / OUTPUT.
  • Convert each process to an assignment or calculation using ←.
  • Convert each decision to IF … THEN … ELSE … ENDIF or CASE OF … ENDCASE.
  • Convert every repeated path to the appropriate FOR, WHILE or REPEAT loop.

  • Keep the same sequence, conditions and loop boundaries as the source design.
  • Trace at least one normal and one boundary input to confirm that each path gives the intended output.

Constructs

Cambridge syntaxMatch each construct to its end keyword
Selection IF, ELSE and nested IF
  • A nested IF is a complete IF … ENDIF inside another branch.
IF Mark >= 80 THEN OUTPUT "Distinction" ELSE IF Mark >= 50 THEN OUTPUT "Pass" ELSE OUTPUT "Fail" ENDIF ENDIF
Selection CASE
  • Use CASE OF when one selector is compared with several listed values; place OTHERWISE last.
CASE OF Choice 'A' : OUTPUT "Add" 'D' : OUTPUT "Delete" OTHERWISE : OUTPUT "Invalid" ENDCASE
Count-controlled FOR loop
FOR Index ← 1 TO 10 OUTPUT Index NEXT Index
Pre-condition WHILE loop
  • The condition is tested before the body, so the body may execute zero times.
WHILE Password <> "Open" INPUT Password ENDWHILE
Post-condition REPEAT loop
  • The condition is tested after the body, so the body executes at least once.
REPEAT INPUT Password UNTIL Password = "Open"
Exam trap: WHILE uses a continuation condition; UNTIL uses the condition that stops repetition. Both loops must be able to terminate.

LoopWhen better suitedCreditworthy justification
FORNumber of repetitions is knownThe loop is count-controlled; start and end values define the exact number of iterations.

Structured Programming

Definition + syntaxA procedure is called as a statement
Definition What a procedure is
  • A procedure is a named subroutine / module that performs a specific task.
  • It does not return one value for use in an expression; results can instead be produced through output or reference parameters.
Syntax Define and call
PROCEDURE DisplayTotal(Total : REAL) OUTPUT "Total: ", Total ENDPROCEDURE CALL DisplayTotal(GrandTotal)
Exam trap: use CALL for a procedure. Do not write RETURN unless the supplied procedure specification explicitly requires a different mechanism.
Syntax checked against9618/23 O/N 2022 · MS
When to use + benefitsName the task in the scenario
When to use Appropriate location
  • Use a procedure for a distinct task that does not need to supply one return value to an expression.
  • Use it where the same sequence is required more than once, such as validation, displaying a menu or printing a report.
Benefits Why it improves the algorithm
  • Avoids duplicated code and supports reuse.
  • Makes the algorithm modular, so each task is easier to read, test, debug and maintain.
Exam precision: a strong answer names both the exact task and why a procedure suits it—for example, “use a procedure to display the menu because it is repeated and returns no value.”
Purpose + passing modesBYVAL and BYREF have different effects
Purpose Why parameters are used
  • Parameters provide an interface through which the calling program passes data to or from a subroutine.
  • A procedure can have no parameters, one parameter or several parameters; declarations specify their order and data types.
ModeWhat is passedEffect on caller
BYVALA copy of the argument’s valueChanging the parameter does not change the original variable.
BYREFA reference / address to the original variableChanging the parameter changes the caller’s variable.
Syntax Reference and value parameters
PROCEDURE AddBonus(BYVAL Bonus : REAL, BYREF Pay : REAL) Pay ← Pay + Bonus ENDPROCEDURE CALL AddBonus(50.00, WeeklyPay)
Exam trap: BYREF is appropriate only when the subroutine must alter the caller’s variable. Do not claim that BYVAL changes the original.

Definition + syntaxA function call is replaced by its value
Definition What a function is
  • A function is a named subroutine that returns one value.
  • Its call is used in an expression; the returned value replaces the call.
Syntax Define, return and use
FUNCTION Larger(A : INTEGER, B : INTEGER) RETURNS INTEGER IF A > B THEN RETURN A ELSE RETURN B ENDIF ENDFUNCTION Largest ← Larger(First, Second)
Exam trap: include the return data type in the header, a value of that type after RETURN, and ENDFUNCTION.
Syntax checked againstOfficial specimen MS · functions
When to useThe required result should be one value
Appropriate use Where a function fits
  • Use a function when a subtask must calculate or determine one value for the rest of the algorithm.
  • Use the function call within an assignment, expression, output statement or condition.
  • Examples include calculating a total, converting a value, or returning TRUE / FALSE after validation.
Benefits Why it helps
  • Encapsulates a calculation once, allowing reuse and independent testing.
  • Gives a long calculation a meaningful name, improving readability and maintainability.
Procedure or function? Choose a function when the caller needs one returned value in an expression; choose a procedure for a task that is called as a separate statement.
Exact terminologyDo not interchange parameter and argument
TermMark-ready meaning
HeaderThe first line that gives the subroutine’s name, formal parameters and, for a function, its return type.
InterfaceThe defined way the subroutine exchanges data with its caller: its parameters and return value.
ParameterA formal named placeholder declared in the subroutine header.
ArgumentThe actual value, variable or expression supplied when the subroutine is called.
Return valueThe single result sent back by a function; it replaces the function call in an expression.
Example: in Largest ← Larger(First, Second), A and B are parameters; First and Second are arguments.
Terminology checked againstOfficial syllabus · 11.3 guidance
Efficiency checklistCorrectness first, then remove unnecessary work
Runtime / work Reduce unnecessary operations
  • Avoid unnecessary passes through data and repeated calculations whose result can be stored.
  • Stop searching or iterating once the required result is found, where the algorithm permits this.
  • Choose a loop whose control matches the task and ensure it has a clear termination condition.
Structure Avoid duplicated code
  • Move repeated logic into a reusable procedure or function.
  • Use suitable variables, constants and data structures rather than duplicating the same value or logic.
Clarity Make correctness maintainable
  • Use meaningful identifiers, consistent indentation and the simplest suitable construct.
Exam precision: “shorter code” is not automatically more efficient. Explain the saved work—for example, fewer iterations, no repeated calculation or no duplicated block.

Program Development Life cycle

Purpose + benefitsState what the framework controls
Definition What a development life cycle is
  • A development life cycle is a structured sequence of stages used to plan, create, test, deliver and maintain a program.
Purpose Why it is used
  • Ensures development is systematic and that essential activities are not omitted.
  • Defines the outputs / deliverables of each stage so the next stage has the information it needs.
  • Allows time, cost, staff and other resources to be planned and progress monitored.
  • Provides documentation and review points so faults or misunderstood requirements can be found before later work depends on them.
Overall benefit The intended result
  • Increases the chance that the finished program is fit for purpose, reliable and meets the agreed requirements.
Exam precision: “it helps make software” is too vague. Name a controlled feature such as stages, resources, documentation, progress or requirements.
Scope checked againstOfficial syllabus · 12.1
Need + selectionThere is no universally best model
Need Why different models exist
  • Programs differ in size, complexity, risk, deadline and available resources.
  • Requirements may be fixed and fully known or may change as users see working versions.
  • Projects differ in the amount of client involvement, documentation and early delivery required.
ChooseWhen it is most suitableScenario clue
WaterfallRequirements are stable, complete and unlikely to change; strong documentation or formal approval is required.Fixed contract, regulated or predictable project
IterativeA useful subset can be delivered first and requirements can be refined through repeated feedback.Evolving requirements; incremental releases
RADThe deadline is short, the system can be split into modules, skilled teams and users are available for rapid prototyping.Time-critical; intensive user feedback
How to justify a choice: write model + project fact + consequence. For example, “Use RAD because the modules can be developed in parallel, allowing an early prototype before the fixed launch date.”
Scenario wording checked against9618/21 M/J 2023 · Q59618/23 M/J 2022 · Q8
Three-model comparisonPrinciple ≠ benefit ≠ drawback
Waterfall · Principle Linear and sequential
  • Each stage is completed and approved before the next stage begins; its output is passed to the next stage.
  • Returning to an earlier stage is limited and normally requires formal change control.
Waterfall · Benefits Why it can work well
  • Clear stages, milestones and deliverables make the project easy to plan, manage and monitor.
  • Produces detailed documentation and works well when requirements are stable.
Waterfall · Drawbacks What can go wrong
  • It is difficult / slow to accommodate changing requirements after a stage has been completed.
  • There is no working software until late, so user misunderstandings and faults may be discovered late and the product may be slower to market.
Iterative · Principle Repeated development cycles
  • A simple subset of the requirements is developed first; repeated cycles expand or improve it until the full program exists.
  • Each iteration produces a working version that is tested and reviewed; feedback informs the next iteration.
Iterative · Benefits Why repeated versions help
  • Provides working software early and exposes risks, faults and misunderstood requirements sooner.
  • Allows user feedback and changes to be incorporated between iterations.
  • Smaller increments are easier to test and debug.
Iterative · Drawbacks Management costs
  • Repeated feedback may cause scope creep, making final cost and completion time harder to predict.
  • Iterations require continued user involvement and careful integration; repeated changes may create rework or weak overall design.
RAD · Principle Parallel prototypes
  • Modules are developed in parallel as prototypes, with minimal detailed up-front planning.
  • Users are involved throughout; prototypes are repeatedly reviewed and refined.
RAD · Benefits Speed and flexibility
  • Parallel work and reusable components allow quicker development and an early working prototype.
  • Frequent user feedback makes it easier to change requirements and improve usability.
RAD · Drawbacks Conditions and risks
  • Requires skilled developers, modular requirements and high, continuous user involvement.
  • Minimal planning can cause weak documentation or architecture; frequent changes make cost and completion time difficult to estimate.
Exam trap: iterative and RAD are not identical. Iterative development emphasises repeated increments; RAD specifically emphasises rapid prototyping, parallel module development and intensive user involvement.

Purpose What the diagram records
  • Shows every possible state of a system / algorithm and the permitted transitions between states.

Program Testing and Maintenance

Expose ≠ avoidDetection techniques and prevention practices
Expose faults Make hidden errors observable
  • Use planned test cases with known expected results, including normal, abnormal and boundary values; compare expected with actual output.
  • Perform a dry run / walkthrough and record variable values in a trace table to find the first unexpected value or path.
  • Use a debugger: set a breakpoint, single-step statements and inspect variables in a watch window.
  • Use white-box testing to execute every logic path and black-box testing to check behaviour against the specification.
  • Test modules separately, then use integration testing to expose interface / parameter-passing faults.
Avoid faults Reduce the chance of introducing errors
  • Use a clear modular design, stepwise refinement, meaningful identifiers and consistent indentation so the logic is easier to inspect.
  • Use suitable data types, constants, local variables and input validation to prevent invalid values reaching unsafe operations.
  • Reuse tested library routines / modules instead of rewriting reliable logic.
  • Test each module as it is developed and use peer review / walkthroughs before modules are integrated.
  • Use IDE features such as dynamic syntax checking, auto-completion and auto-indentation to expose mistakes while code is written.
Exam precision: testing can reveal the presence of faults, not prove their complete absence. Always explain what the method observes—an unexpected output, variable value or execution path.

Debugging workflowReproduce → locate → repair → retest
1 · Reproduce Make the fault repeatable
  • Record the exact test data, expected result and actual result that expose the fault.
2 · Locate Find the first wrong step
  • Narrow the fault to a module / path, then use messages, a trace table or breakpoint + single-step + watch to find the first incorrect statement or value.
3 · Correct Repair the cause
  • Syntax: change the statement to match the language grammar.
  • Logic: correct the algorithm, condition, expression or loop boundary.
  • Run-time: validate data or guard the operation—for example, check a divisor is non-zero or an index is in range.
4 · Retest Prove the repair did not break anything else
  • Rerun the failing test and relevant boundary cases, then perform regression testing on previously working functions.
  • Update the test record and program documentation.
Exam precision: correcting the visible output without fixing the cause is not enough. The same test must now pass and existing behaviour must remain correct.

Safe enhancement workflowUnderstand existing behaviour before changing it
Analyse Establish the current system
  • Read the requirements, design, code and documentation to identify the relevant modules, data structures, parameters and interfaces.
  • Run existing tests and representative data to establish a baseline of correct current behaviour.
  • State the new requirement precisely and analyse its effect on callers, files, validation, outputs and other dependent modules.
Amend Implement the enhancement
  • Change or add the smallest suitable module while preserving existing interfaces where possible.
  • Update declarations, validation, parameters / return values and documentation consistently.
  • Add test cases for the new functionality, including normal, abnormal and boundary data where relevant.
Verify Protect existing functionality
  • Test the amended module, then perform integration testing with modules that call it or receive its output.
  • Perform regression testing so functions that previously worked still give the same correct results.
Exam precision: “add the new code” is incomplete. A safe amendment includes impact analysis, updated tests and proof that existing behaviour has not been damaged.
